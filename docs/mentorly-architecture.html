01 Overall Runtime Architecture

Architecture Style

Modular Monolith — single Spring Boot JAR with 31 domain packages, each containing Controller → Service → Repository.

Key Design Patterns: Strategy (PaymentGateway), Observer (Notifications), Guard (ProfileCompletionGuard), IdempotencyKeySupport, AOP Audit Logging.

Runtime Stack

Backend: Java 21 · Spring Boot 3.2 · Spring Security 6 · Spring Data JPA · Hibernate · Flyway 78 migrations · Micrometer

Frontend: React 18 · Vite · React Router · React Context (no Redux) · WebSocket native

Infra: Docker Compose · Nginx · MySQL 8.0 · Let's Encrypt SSL · GitHub Actions CI/CD · GHCR

02 Authentication & Session Management

What Starts the Flow

User visits /login or /signup → AuthPage.jsx renders.

Step-by-Step

1. AuthPage → POST /api/v1/auth/signup or /login

2. AuthController → AuthService → BCrypt verify/hash

3. OtpService (email verification for signup)

4. JwtService generates access + refresh tokens

5. RefreshTokenSession stored in DB (httpOnly cookie)

6. LoginAttemptRecorder tracks failed attempts

7. ProfileCompletionGate checks profile completeness

8. Role decision → Learner / Mentor / Admin workspace

Key Decisions

OTP Required? → Email verification for new signups

Profile Complete? → Redirect to ProfileSetup if incomplete

Role? → Routes to appropriate workspace

Failure Paths

• Bad credentials → AuthAttemptRecorder → 401

• Disabled account → 403

• Duplicate email → DataIntegrityViolation → 409

• OAuth2 failure → OAuth2LoginFailureHandler

03 Mentor Verification

What Starts the Flow

Mentor clicks "Become a Mentor" → submits verification application with documents.

Step-by-Step

1. Mentor submits verification request via MentorVerificationController

2. MentorVerificationService checks if already verified/requested

3. Creates MentorVerificationRequest (status=PENDING)

4. Documents uploaded via StoredFileService (Optional documents per V53)

5. Admin reviews via AdminController / MentorVerificationsPage

6. Admin approves/rejects/requests more info

7. On approval: user role upgraded, notification sent

Key Decisions

• Already verified? → Reject duplicate requests

• Admin decision: APPROVE / REJECT / REQUEST_INFO

Failure Paths

• Incomplete profile → ProfileCompletionGuard blocks submission

• Missing required docs → Validation error

• Rejected → Can re-apply after cooling period

Source Files

MentorVerificationController.java — REST API
MentorVerificationService.java — Business logic (45 @Service)
MentorVerificationRequest.java — Entity (mentor_verification_requests)
SkillVerificationController.java — Skill assessment API
SkillVerificationTask.java — Task entity
SkillVerificationSubmission.java — Submission entity
StoredFileService.java — Document storage
AdminController.java — Admin moderation queue
MentorVerificationsPage.jsx — Admin UI
BecomeMentorPage.jsx — Mentor application UI

Key Architecture Decision

Verification is a separate flow from profile completion. Mentor must complete profile FIRST, then apply for verification. Admin approval is required before mentor can receive bookings.

04 Discovery & Search

What Starts the Flow

Learner browses /mentors or searches by skill → LearnerMentorsPage.jsx renders SearchFilters.

Step-by-Step

1. SearchFilters captures query, skill, rating, price range

2. GET /api/v1/users/mentors (public, no auth required for listing)

3. MentorSearchController → JPA Criteria API with FULLTEXT index

4. Results → Mentor Card components rendered

5. Click mentor → GET /api/v1/users/mentors/{id} (authenticated)

6. Full profile: reviews, certifications, availability, sessions

Key Decisions

• Fulltext match? → MySQL FULLTEXT index (V18)

• Skill filter? → JOIN skills table

• Auth required for full profile? → Yes, anonymous gets 401

05 Availability → Skill Session Generation

What Starts the Flow

Mentor opens MentorCalendarPage → adds availability slot → system may auto-generate SkillSessions.

Step-by-Step

1. Mentor adds time slot via AvailabilityController

2. Validate: no overlap, future time, mentor role required

3. UserAvailabilitySlot saved to user_availability_slots table

4. SessionAutoCreationService may auto-create SkillSession

5. SkillSession saved with status=AVAILABLE, type=SKILL

6. PUBLIC sessions listed in learner discovery

7. PRIVATE sessions accessible via invite link only

Key Decisions

• Overlap exists? → Reject slot creation

• Session type: PUBLIC → listed · PRIVATE → invite only

• Past slot? → Auto-expire by BookingLifecycleScheduler

06 Booking — Deep Flow (8-Step Validation)

Step-by-Step Validation Chain

① Idempotency: BookingIdempotencyKey check → replay returns existing booking

② Session: EXISTS? → AVAILABLE? → start_time in future?

③ Self-book: learner_id ≠ mentor_id

④ Capacity: group session count < max_participants

⑤ Duplicate: UNIQUE(learner_id, session_id) check

⑥ Mentor: verified=true, enabled=true

⑦ Block: not in UserBlock table

⑧ Profile: ProfileCompletionGuard check

Key Source Files

BookingController.java — REST API
BookingService.java — Create + validate
BookingLifecycleService.java — State transitions (919 lines)
BookingApprovalController.java — Mentor approval
BookingIdempotencyKey.java — Idempotency entity
Booking.java — Entity
BookingFlowPage.jsx — Frontend booking UI
PaymentService.java — Payment orchestration
PaymentGateway.java — Strategy interface
StripeAdapter.java — Stripe implementation
RazorpayAdapter.java — Razorpay implementation
StripePaymentForm.jsx — Card input component

Key Architecture Decision

Booking uses Strategy Pattern for payment gateways. BookingService delegates to PaymentService, which selects the adapter. All 8 validations run in a single transaction — any failure rolls back the entire operation.

07 Session Completion & Dispute

What Starts the Flow

Either participant marks session complete via BookingLifecycleService.completeBooking().

Step-by-Step

1. Participant calls POST /bookings/{id}/complete

2. BookingLifecycleService checks both participants confirmed

3. Both confirmed → Booking = COMPLETED

4. Payment = RELEASED (escrow released)

5. Platform fee calculated (configurable %)

6. Mentor earning = amount - fee

7. WalletService.addEntryForUser(EARNING) updates wallet

8. CertificationService checks if learner earns certificate

Failure / Dispute

• One party disputes → AdminSessionDisputesPage

• Admin decides: Refund (return to learner) or Release (pay mentor)

• Escrow is NEVER released before legitimate completion

Source Files

BookingLifecycleService.java — completeBooking(), startBooking()
WalletService.java — EARNING entry
CertificationService.java — Progress check
PaymentService.java — Escrow release
AdminSessionDisputesPage.jsx — Admin dispute UI
LearnerSessionsPage.jsx — Session completion UI

What Starts the Flow

Step-by-Step

2. SessionRequestService creates SessionRequest entity

3. Mentor notified via WebSocket + Email

5. On accept: Mentor creates SkillSession → normal booking flow

11 Communication — Booking Chat + Direct Messaging

Two Communication Channels

Booking Chat: Scoped to a booking, available to both participants. Uses /ws/chat WebSocket.

Direct Messaging: Peer-to-peer, requires MessageRequest approval. Uses /ws/chat/direct WebSocket.

Step-by-Step (Booking Chat)

1. WebSocket connection: /ws/chat with bookingId

2. BookingChatWebSocketHandler verifies participant

3. ChatService + ChatInputSanitizer (XSS prevention)

4. ChatMessage saved to DB

5. WebSocket broadcast to other participants

6. Read receipts and reactions tracked

Privacy Rules

• UserBlock check prevents blocked users from messaging

• MessageRequest required before DM (privacy model)

• Block → immediate message prevention

12 Notifications

What Starts the Flow

Any business event (booking confirmed, payment received, message sent, etc.) calls NotificationService.notifyUser().

Step-by-Step

1. Business service calls NotificationService.notifyUser(userId, type, title, message)

2. NotificationPreference check (per-type, per-role settings)

3. AppNotification persisted to DB (app_notifications table)

4. WebSocket push via NotificationWebSocketHandler.broadcastToUser() (real-time)

5. Email branch: EmailNotificationService (preference-gated)

Special Paths

• Admin Broadcast → NotificationBroadcastPage → all users

• Scheduled Reports → AdminScheduledReportService (cron-based)

13 Learning — Aggregated Capabilities

What It Is

Learning is an aggregation of capabilities, not a single CRUD flow. It includes notes, tasks, paths, achievements, and certificates.

Components

• Session Notes: Learners take notes per session (SessionNote entity)

• Learning Paths: Curated sequences of sessions (LearningPath entity, V61)

• Learner Tasks: Homework/tasks assigned by mentor (LearnerTask entity)

• Daily Tasks: Daily learning activities (V63)

• Achievements: Milestone tracking

• Certificates: Auto-issued on completion (CertificationService)
